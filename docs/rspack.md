
# Rspack 종합 보고서

## 1. 개요 (Introduction)

### 1.1 Rspack이란?

• Rspack은 Rust로 구현된 고성능 JavaScript 번들러로, 발음은 “/ˈɑrəspæk/”입니다.
• 웹팩(webpack) 생태계와 높은 호환성을 가지면서도, Rust 특유의 빠른 빌드 속도를 강점으로 내세웁니다.
• ByteDance(바이트댄스)에서 복잡한 대규모 프로젝트 빌드를 최적화할 목적으로 처음 개발하였으며, 현재 오픈소스로 공개되어 있습니다.

### 1.2 왜 Rspack인가?

Rspack은 특히 대규모 모놀리식 앱에 대해 속도 개선 및 유연한 커스터마이징을 제공하기 위해 탄생했습니다.

1) **개발 모드(Dev mode) 속도**
   - “npm run dev” 같은 프로젝트 개발 서버 구동은 엔지니어가 하루에도 수십 번씩 반복하는 명령입니다.
   - 스타트업 시간을 10~15초 이하로 줄이지 못하면 개발 생산성이 크게 떨어집니다. Rspack은 빠른 Cold Start 및 HMR(Hot Module Replacement)을 지원하여 이 문제를 해결합니다.

2) **빌드 속도**
   - “npm run build”와 같은 프로덕션 빌드 명령은 CI/CD 파이프라인에서 자주 실행되며, 대규모 앱에서는 20~30분 이상의 시간이 걸릴 수도 있습니다.
   - Rspack은 Rust 기반의 병렬 처리 구조를 통해 빌드 시간을 대폭 단축합니다.

3) **유연한 구성 (Flexible configuration)**
   - 실제 기업 현장에서 사용하는 복잡한 구성(코드 스플리팅, 커스텀 로더, 플러그인 등)을 대응하려면 설정 확장성이 매우 중요합니다.
   - Rspack은 webpack과 유사한 설정 방식을 가지고 있어, 기존 webpack 프로젝트의 마이그레이션 장벽을 낮춥니다.

4) **고급 최적화 (Production optimization)**
   - 대규모 앱 환경에서 세분화된 코드 스플리팅, 멀티쓰레딩 최적화 등을 새롭게 설계해, Rust 생태계의 이점을 살린 고성능 빌드를 구현했습니다.

## 2. Rspack의 현재 상태와 목표

### 2.1 Rspack 1.0

• 2024년 8월 기준, Rspack은 1.0 버전을 발표하여 “프로덕션 환경에서 사용 준비가 된” 번들러임을 공식적으로 선언했습니다.
• webpack이 가진 대부분의 API와 기능을 커버하도록 발전해왔으며, 커뮤니티가 가장 많이 사용하는 로더(loaders)의 대부분이 Rspack에서 호환되는 것으로 알려져 있습니다.
• 상위 50개의 인기 webpack 플러그인 중 80% 이상이 곧바로 사용 가능하거나 별도 대안이 제공됩니다.

### 2.2 향후 로드맵 (The future of Rspack)

• 아직 webpack이 제공하는 “모든” 기능을 100% 동일하게 지원하지는 않습니다. Rspack 팀은 커뮤니티 피드백을 바탕으로, 부족한 부분을 지속적으로 보완하겠다고 밝힌 상태입니다.
• 프레임워크 팀이나 툴체인(React, Vue, Next.js, Remix 등)과 협업해, Rspack의 성능 이점을 극대화할 수 있는 솔루션을 제공할 계획입니다.
• 플러그인 아키텍처도 고성능 구현에 초점을 맞추고 있으며, 기존 webpack의 훅(hook) 구조가 가지는 병목을 줄이는 방안을 탐색 중입니다.

## 3. Rspack의 특징

### 3.1 Rust 기반 고성능

• Rust는 메모리 안전성과 멀티쓰레딩 효율이 뛰어난 언어로, GC(가비지 컬렉션)가 없으면서도 높은 성능을 발휘합니다.
• Rspack은 Rust의 병렬 처리를 적극 활용하여, 큰 규모의 코드를 여러 코어에 분산해 빠르게 빌드합니다.

### 3.2 웹팩(webpack)과의 높은 호환성

• Rspack이 웹팩을 완전히 대체할 수 있도록, 설정 파일 형식과 주요 개념(entry, output, loaders, plugins 등)을 최대한 유지합니다.
• 웹팩 로더와 플러그인이 상당 부분 그대로 동작하도록 설계되었지만, 100% 호환을 장담하지는 않으므로 사용 전 호환 여부를 반드시 확인해야 합니다.

### 3.3 멀티코어 병렬화 아키텍처

• Node.js로 구동되는 웹팩이 싱글 쓰레드 기반이라면, Rspack은 Rust를 통해 멀티쓰레드를 풀로 활용합니다.
• 빌드 과정에서 CPU 리소스를 모두 활용하므로 대규모 프로젝트에서 확실한 속도 향상을 체감할 가능성이 큽니다.

### 3.4 필수 기능의 내장 구현

• 웹팩은 로더와 플러그인 생태계가 굉장히 넓은 대신, 종종 성능 문제를 유발하는 서드파티 패키지들이 섞여 있을 수 있습니다.
• Rspack은 핵심 기능(소스 맵, 코드 압축, HMR, 코드 스플리팅, tree-shaking 등)을 내부적으로 최적화된 Rust 코드로 제공하여, 병목 지점을 줄이도록 설계했습니다.

### 3.5 Hot Module Replacement(HMR) 최적화

• 대규모 프로젝트에서 HMR 성능은 개발 경험을 큰 폭으로 좌우합니다.
• Rspack은 증분 컴파일 전략을 적용하여, 변동된 부분만 신속히 재번들링해 개발 모드에서 개발자 생산성을 높입니다.

## 4. 다른 번들러와의 비교

### 4.1 Webpack 대비

• **Rust 언어 효율**: Webpack은 JS/TS로 작성되어, 프로젝트 규모가 커질수록 빌드 시간이 길어지는 경향이 있습니다. Rspack은 Rust 실행 속도와 멀티쓰레드 처리를 통해 이를 개선합니다.
• **생태계 성숙도**: Webpack은 매우 오래된 생태계를 보유, 다양한 플러그인/로더가 존재합니다. Rspack은 초기 단계 대비 빠르게 성장 중이나, 여전히 Webpack 대비 제한적인 면이 있습니다.
• **마이그레이션 비용**: Rspack은 Webpack 생태계와 유사한 사용성을 제공하지만, 일부 플러그인이나 기능 호환성에서 문제가 생길 수 있어 주의가 필요합니다.

### 4.2 Vite 대비

• Vite는 개발 서버에 esbuild(Go 기반)를 사용하고, 프로덕션 빌드는 Rollup을 활용하는 구조입니다.
• Rspack은 한 번에 Rust 기반 빌딩 과정을 모두 수행하므로, Rollup 수준의 유연함이나 설정보다 “고성능 멀티쓰레딩 빌드”에 강점이 있습니다.
• Rollup 단계에서 발생하는 JS 기반 연산 한계를 Rspack은 Rust로 극복하고자 합니다.

### 4.3 esbuild 대비

• esbuild는 Go로 구현되어 매우 빠른 성능을 보이지만, Webpack처럼 HMR이나 세분화된 번들 최적화(특히 optimization.splitChunks 등)에서 기능이 제한적입니다.
• Rspack은 Webpack API 호환성을 목표로 하여, 좀 더 풍부한 확장성과 설정 능력을 지닌 반면, esbuild만큼 minimal & lightweight하지는 않을 수 있습니다.

### 4.4 Turbopack 대비

• Turbopack도 Rust로 구현되었으나, Webpack과 호환성을 포기하고 아키텍처를 재설계했다는 점이 큰 차이입니다.
• Rspack은 Webpack 기반 레거시 프로젝트의 전환, 점진적 마이그레이션에 적합하도록 설계되었습니다.
• Turbopack은 Next.js(버셀) 생태계에 긴밀히 연결되어 있고, 아직 초기 개발 단계입니다.

### 4.5 Rollup 대비

• Rollup은 라이브러리 번들링에 특화된 도구로, ESM 빌드 아웃풋이 최적화되어 있습니다.
• 반면 Rspack은 대규모 SPA/웹앱 번들링에 초점을 맞추어, HMR, 빠른 프로덕션 빌드, 코드 스플리팅 등 웹앱 기능에 최적화되어 있습니다.
• 대규모 프로젝트에서는 Rollup 기반인 Vite를 적용하는 케이스가 많지만, Rspack은 Rust 최적화를 통해 더 빠른 빌드를 추구합니다.

### 4.6 Parcel 대비

• Parcel 역시 “자동화된” 아키텍처를 내세워 별도의 설정 없이도 많은 기능을 지원합니다.
• Rspack은 Parcel과 전체 구조가 비슷하나, Parcel은 “Out-of-the-box” 접근에 중점을 두는 반면 Rspack은 “Webpack 호환 + Rust 고성능”에 방점을 찍습니다.
• Parcel이 가진 HTML/CSS 자산을 1등 시민으로 다루는 아이디어나 Unified Graph 등의 혁신은 Rspack에서도 검토 중이라고 알려졌습니다.

## 5. 도입 시 고려사항

### 5.1 Config 및 플러그인 호환성 점검

• 목표는 Webpack 대체나 보완이지만, 아직 일부 Webpack 플러그인은 그대로 100% 동작하지 않을 수 있습니다.
• 본격 도입 전, 파일럿 프로젝트를 통해 로더·플러그인 호환 상태를 반드시 확인해야 합니다.

### 5.2 CI/CD 파이프라인 전환 비용

• 기존 Webpack 스크립트를 “rspack build”로 변경하면, 결과물 디렉토리 구조(dist 등)가 달라지는지 확인해야 합니다.
• 캐시나 Artifact 저장 전략도 조정할 수 있으며, 대규모 모놀리식 프로젝트라면 빌드 파이프라인 전환 기간이 필요합니다.

### 5.3 Rust 기반 생태계 이해

• Rspack 자체 설정은 Webpack-like 하므로 JavaScript로 작성 가능하지만, 저수준(Custom plug-ins) 확장은 Rust가 필요할 수 있습니다.
• Rust 언어 학습 곡선이 있을 수 있으며, 사내에 Rust 역량이 얼마나 있는지 점검해볼 필요가 있습니다.

## 6. 결론

Rspack은 ByteDance에서 시작된 Rust 기반의 고성능 번들러로, Webpack과 유사한 구성을 유지하면서도 멀티코어 병렬화를 통해 빠른 빌드를 가능케 한다는 점이 가장 큰 매력입니다.

• Webpack에서의 긴 빌드 시간, 대규모 모놀리식 앱의 느린 HMR 등에 고민이 큰 조직일수록 Rspack 도입 효과를 크게 볼 수 있습니다.
• 다만, 아직 모든 Webpack 플러그인을 완벽히 지원하지 않으므로, 파일럿 프로젝트를 통한 호환성 검증이 필수적입니다.
• Rust에 대한 사내 역량, CI/CD 파이프라인 전환 비용, 주요 플러그인의 호환성 등을 면밀히 살펴보면서 도입을 진행한다면, Rspack이 개발 생산성과 빌드 효율을 동시에 끌어올리는 좋은 대안이 될 것입니다.
